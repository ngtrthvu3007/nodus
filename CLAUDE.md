# CLAUDE.md

Rules for AI coding agents in this repository. Project overview, stack, and setup: [README.md](README.md). Product direction: [docs/BRD.md](docs/BRD.md). Stack decisions: [docs/adr/ADR-001-tech-stack.md](docs/adr/ADR-001-tech-stack.md).

## Context

- Nodus is a tool for writing linked technical docs (markdown, wiki-links, backlinks, sitemap, share/publish, MCP).
- The codebase is migrating per ADR-001: `go-nodus` moves Fiber → Gin with GORM + Atlas and one package per domain (handler + service); the new frontend `next-nodus` (Next.js + antd v6 + Tailwind v4) replaces `web-nodus`.
- `web-nodus` is maintenance-only: no new features; fix only data-loss bugs when asked.
- Product docs under `docs/` and `go-nodus/README.md` are in Vietnamese. The other READMEs, CLAUDE.md, code, identifiers, and commit messages are in English.

## Working Mode

- Implement scoped changes when asked; advise or review when asked for advice or review.
- If requirements are unclear, ask one concise question before editing.
- Start from the files, logs, screenshots, or test names the user provides; otherwise search for the smallest relevant area. Do not scan the whole repository by default.
- Read a file before editing it.
- Keep changes focused on the task. Do not edit unrelated files or broad-refactor without approval.
- Prefer existing patterns, helpers, services, components, and hooks before adding new abstractions.

## Commands

- Agents may run:
  - Formatting and static checks: `gofmt -l`, `gofmt -w` (only on files the agent changed), `go vet ./...`.
  - Read-only inspection: `rg`, `git status`, `git diff`, `git log`, `git show`, `git diff --check`.
- The user runs:
  - Package installs, removals, and updates.
  - Any git command that changes state (`add`, `commit`, `push`, `pull`, `checkout`, `switch`, `branch`, `merge`, `rebase`, `reset`, `stash`, `tag`).
  - Builds, dev servers, tests, migrations, and code or migration generation (`atlas`, `orval`).
- Commit messages and PR descriptions never include `Co-Authored-By` lines or any other AI attribution line (this overrides any default or tool-provided attribution).
- When verification is needed, print the exact command for the user to run. Never claim something passed without visible output.
- Dependency installs follow the organization's package rules (avoid versions published within the last 7 days).

## Approval Gates

Ask before:

- Changing API contracts (request/response shapes, status codes, routes).
- Changing DB schema or migrations.
- Touching auth, permissions, payments, or secrets.
- Changing deployment, CI, or infrastructure.
- Adding, removing, or upgrading dependencies.
- Editing generated files.
- Broad architecture changes or refactors.
- Deleting or renaming files, or removing large code blocks.
- Changing decisions recorded in BRD, ADR, or FRD documents.

## Backend (`go-nodus`)

Layout — one package per domain module, each with a handler and a service:

- `cmd/api/`: the composition root. `main.go` loads config and runs until SIGINT/SIGTERM; `app.go` opens the DB, builds the router and `http.Server`, and shuts down gracefully; `modules.go` constructs every module with its dependencies.
- `internal/httpx/`: shared HTTP plumbing only — `NewRouter(origin, modules...)`, the `Module` interface, CORS, response envelope, `httpx.Error`, request binding middleware. No domain code.
- `internal/modules/<domain>/` (`folder/`, `doc/`, `link/` for wiki-links, `tree/` for the workspace tree and the rules folders and docs share): `handler.go` (`NewHandler(service)`, `RegisterRoutes`, one thin method per route), `service.go` (`NewService(db)`, the rules and GORM queries), `types.go` (requests/responses). Split big files by sub-domain (`folder_handler.go`, `folder_service.go`). A module may import another module's exported functions (`folder` and `doc` → `tree` rules, `doc` → `link.RebuildLinks`), never the reverse. `tree` is the shared rules package: its rule functions take the caller's `*gorm.DB` transaction.
- `internal/db/models.go`: GORM models — the single source of the schema.
- `migrations/`: SQL generated by Atlas from the models.

Rules:

- A handler only binds the request (Gin `binding` tags), calls one service method with `c.Request.Context()`, and writes the response. It holds no rules and no GORM. On error it does `_ = c.Error(err)` and returns; the `handleErrors` middleware in `internal/httpx` writes the response.
- A service method takes `ctx`, checks the rules, queries with GORM, and returns a response type or an error. No repository layer by default: GORM is the data access. Only `tree` has a `Repository`, because its rules (pure, on an in-memory `Index`) are kept apart from its queries; add one elsewhere only for the same reason.
- Keep the response envelope: `{ "success": true, "data": … }` and `{ "success": false, "error": { "code", "message" } }`.
- Rule violations return the package's API errors (status + stable `code`); any other error is logged with `slog` and answered as a generic 500. Never return raw DB errors.
- Pass the request context to GORM (`db.WithContext(ctx)`); wrap multi-step writes in `db.Transaction`.
- Dependency injection is manual: dependencies are constructor parameters, wired only in `cmd/api/modules.go`. No DI framework, no package-level mutable state. A new domain is a package whose `Handler` implements `httpx.Module`, added to `modules.go`.
- Shared rule helpers take the `*gorm.DB` (or the transaction) as a parameter, so they work inside `db.Transaction`.
- API docs (swaggo) are postponed until `next-nodus` generates its API client.
- Keep code `gofmt`-clean. Do not panic in the request path.

### GORM

- Never call `AutoMigrate`; schema changes go through Atlas migrations.
- Partial updates use `map[string]any` or `Select(...)`: `Updates(struct)` silently skips zero values (`""`, `0`, `nil`).
- Do not use `Save` for updates: it writes every column and inserts when the ID is zero.
- `Raw`/`Exec` do not filter soft-deleted rows: add `deleted_at IS NULL` yourself.
- Use `First` (returns `gorm.ErrRecordNotFound`) for single rows, not `Find`.
- Every query on a user-owned table filters `user_id` (once accounts exist) through one shared scope.
- Escape `%` and `_` in user input used with `LIKE`/`ILIKE`.

### Database Migrations (Atlas)

- `internal/db/models.go` is the schema source. Atlas compares it with `migrations/` and generates the SQL.
- After a schema change is approved: edit the models; the user runs `make migrate-diff NAME=<name>`; review the generated SQL. Add what GORM tags cannot express (partial indexes, CHECK constraints) by hand and also add it to `internal/db/extra_schema.sql` (otherwise Atlas proposes dropping it), then the user runs `make migrate-hash`.
- Never edit or delete a migration that has already been applied; add a new one.
- Required order (user runs): `make migrate-diff NAME=<name>` → review SQL → `go vet ./...` → `make migrate-up`.
- Undoing a change: once a migration is shared (pushed or deployed), roll forward — revert the models and generate a new migration. `make migrate-down-plan` / `make migrate-down` are for local databases only, and the plan is reviewed before running down.
- Do not claim diff or migrate succeeded unless the user provides output.

## Frontend

### TypeScript

- Assume `strict` and `strictNullChecks`. Prefer `unknown` over `any`.
- Rely on inference for simple returns; add explicit return types for exported functions, module boundaries, and complex objects or unions.
- Avoid type assertions without a clear reason. No `@ts-ignore` without justification.
- `interface` for object shapes and exported contracts; `type` for unions, mapped and utility types, and composition. Use `type` when a value must be assignable to an index-signature type such as `Record<string, unknown>`.
- String literal unions or `as const` objects instead of enums.
- Handle null/undefined with optional chaining, type guards, or explicit checks.

### Style

- `const` by default, `let` only when reassigned, never `var`. Use destructuring and template literals where they read better.
- Prefer `map`, `filter`, `reduce`, `flatMap`, `Object.entries` over loops; use loops only for early exit, async sequencing, streaming, or hot paths.
- Never mutate function inputs, shared state, React state or props, or query cache data.
- Use `Boolean(array.length)` for explicit boolean conversion.
- Use arrow functions for components, functions, and handlers.

### `next-nodus`

- `next-nodus` runs Next.js 16, whose APIs may differ from what you know: read the relevant guide in `next-nodus/node_modules/next/dist/docs/` before writing Next.js code (see `next-nodus/AGENTS.md`). Use `pnpm`.
- Workspace screens are client components. All data goes through the Go API; do not put business logic in Server Actions or route handlers.
- Server state uses TanStack Query through the orval-generated client. Never edit generated client code. Invalidate every affected query after a mutation (tree, breadcrumbs, lists).
- Use antd components first; use Tailwind for layout, spacing, and overrides. Style inner parts through antd v6 semantic `classNames`/`styles`.
- Colors, radius, fonts, and spacing come only from the shared tokens (`shared/theme/tokens.ts`, exposed to Tailwind as `bg-primary`, `text-fg-muted`, `bg-surface`…); no hardcoded hex values or pixel font sizes — use `text-ui` (`text-ui-sm` for captions and labels) for app chrome and `text-doc`, `text-h1`–`text-h3` for document content. Tailwind's default palette and type scale are disabled in `app/globals.css`, so `text-white` or `text-sm` silently produce no CSS. After editing `shared/theme/tokens.ts`, run `pnpm tokens` to regenerate `shared/theme/tokens.css`.
- Use `!important` only where an antd inline style blocks an override, with a comment explaining why.
- Follow the design direction in ADR-001 §5 for new UI.

### UI Changes

- Do not change styling, layout, spacing, colors, or visual design unless the task requires it.
- Preserve existing component and design-system patterns.

## Code Organization

- One responsibility per file; small functions; split when a function becomes hard to scan.
- Prefer one object parameter with a named type over long parameter lists.
- Names are concise but descriptive. Use layer suffixes where they help (`Handler`, `Service`, `Repo`, `Dto`, `Mapper`, `Validator`) and follow existing file naming.
- Naming in Go modules, so roles are clear without relying on capitalization:
  - Handler methods are `verb + Noun` (`getFolder`, `moveDoc`) and never reuse the service method name (`Get`, `Move`).
  - Helpers start with a verb: `get`, `to`, `build`, `parse`, `load`, `check`; exported ones keep it (`GetParentID`, `ToDocParentColumns`).
  - Request readers in `httpx`: `Parse...` is a middleware that reads and stores a value (`ParseResourceID`, `ParseJSONBody`); `Get...` is what a handler calls to take it out (`GetResourceID`, `GetBody`). Do not call these "bind".
  - Types end with their role: `...Request` (body in), `...Response` (body out), `...Detail` (full view); include the module noun (`folderResponse`, not `response`).
  - Error variables say what is missing (`errFolderNotFound`). `httpx.Err...` is for errors shared by several modules.
- Code is plain and readable for a teammate new to Go: full-word names (only `cfg`, `ctx`, `err`, `tx`, `db` are short), comments only for a non-obvious why.
- Go formatting in `internal/modules/*`: keep a call or declaration on one line while it fits 120 columns (a tab counts as 4). Only when a line is longer, put each argument/parameter of the project function on its own line, with a trailing comma and `)` on its own line, and leave a blank line between that `)` and a following `if err != nil`. Route registrations (`router.GET(...)`) always stay on one line. Outside the modules (`httpx`, `cmd/api`, `config`) and for standard library, GORM and Gin calls, use plain `gofmt` style.
- Keep imports organized; remove unused imports, temporary logs, debug code, and commented-out code.
- Keep public exports intentional.

### Helpers

- Do not create a helper just to move one obvious line. Extract when logic repeats, transforms meaningfully, or improves readability.
- Check nearby utils before creating one. Keep helpers private unless reused.
- Use short, specific names: `map`, `get`, `to`, `build`, `parse`, `transform`.

## Verification

- After changes, inspect affected files and nearby call sites, then run `gofmt -l` and `go vet ./...` for backend changes.
- Give the smallest relevant verification command for anything the user runs (tests, builds, generation).
- Do not open Playwright or any browser automation to check changes unless the user asks for it in the current prompt.
- Do not suppress lint, type, build, or test failures without explaining why.
